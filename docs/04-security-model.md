# 04 — Security model

## Separation of claims

The project must keep four layers separate:

1. **combinatorial hardness** — properties of a mathematical search problem;
2. **distributional hardness** — hardness on instances actually generated by KeyGen;
3. **primitive security** — one-wayness / indistinguishability of the trapdoor construction;
4. **KEM security** — IND-CPA / IND-CCA style security of the complete scheme.

No layer may be inferred automatically from a lower layer.

## Initial target

Before attempting a full KEM proof, define a minimal one-way trapdoor experiment.

Adversary receives (pk) and a challenge public object generated from random (s). The experiment records whether the adversary recovers (s) or any accepted equivalent witness.

Only after this game is stable should the project define a key-indistinguishability game.

## Eventual KEM goal

If the primitive survives cryptanalysis, an eventual target would be an IND-CCA KEM with explicit invalid-ciphertext handling and domain-separated key derivation.

No such claim currently exists.

## Threat model

Assume an attacker knows:

- the complete specification;
- all algorithms;
- all parameter-generation rules;
- all public transformations;
- arbitrary numbers of public keys and ciphertexts;
- all source code.

Security must not rely on secrecy of the design.

## Side channels

A mathematically sound primitive can still fail through timing, memory access, parser behavior, allocation behavior, or error oracles. Reference code will initially optimize for clarity, but any candidate constant-time implementation must be treated as a separate engineering milestone.

## Falsification criterion

Any polynomial or practically sub-exponential attack that recovers an accepted witness at the proposed parameter sizes is sufficient to reject those parameters or the construction.
